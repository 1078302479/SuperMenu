# 签名与升级后的系统权限

当前本地测试包使用 ad hoc 临时签名。2026-11-12 实测已安装程序的 designated requirement 为 cdhash，本机 `security find-identity -v -p codesigning` 返回0个有效身份。重编译后代码哈希改变，旧辅助功能/自动化授权可能不再匹配；系统设置仍显示开关开启也不能证明当前二进制已经获得授权。

Apple TN3127： https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements

## 后续正式构建

使用同一个有效 Developer ID Application 签名身份，保持应用与扩展的标识、签名要求和安装位置一致。脚本支持：

```sh
SUPERMENU_SIGNING_IDENTITY='Developer ID Application: <certificate name>' \
SUPERMENU_REQUIRE_STABLE_SIGNING=1 \
SUPERMENU_DISTRIBUTION=1 ./scripts/build-local.sh
```

两个 bundle 使用同一指定身份；提供的身份无效时 codesign 会失败，禁止悄悄降级成临时签名。开启 REQUIRE_STABLE_SIGNING 却未指定身份时拒绝生成最终包。当前默认临时签名仍供本地调试，但明确输出重复授权风险。

固定签名身份是改善更新授权连续性的前提，不是自动授予权限或跨系统版本的绝对保证。临时签名切换到正式身份时可能还需最后重新授权一次；应对两个不同代码版本进行覆盖升级验收，不能只测试重复安装相同包。

## 当前处理

- 不直接修改 TCC 数据库，不重置其他权限，不绕过系统授权。
- 区分 AX 权限缺失与事件监听创建失败，避免把两者都说成“检查权限”。
- 本次只修改源码和构建流程，未再次覆盖用户当前程序，避免主动让现有授权失效。
- 未配置签名证书之前，不宣称重复授权问题已经解决。证书、签名要求改变及系统策略都可能要求用户确认。

用户随后选择暂不办理证书，改为明显的自助引导。通用设置已加入橙色提示卡：在云盘入口启用且当前 AX 权限缺失时展开三步重新添加操作；同时保留始终可展开的帮助，包含 macOS 新旧权限页面名称、当前应用定位和立即重检。不会自动移除权限、重置 TCC 或静默授权。该引导版本已编译并覆盖安装到本地，安装前版本保存在 `.build/rollback-cloud-prototype/before-permission-guide-*.backup`，配置未更改，未发布。
